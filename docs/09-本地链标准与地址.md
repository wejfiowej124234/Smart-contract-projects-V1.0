# Part 1：标准流程（原 本地链标准流程）

## 一、合约地址以谁为准？

- **唯一标准**：当前正在运行的节点 + 在本节点上执行过一次部署。合约地址由部署时写入 `deployments/31337.json` 并同步到 `frontend/src/contracts/deployments.json`；前端只读该文件。
- **「链与合约地址不一致」**：多为节点重启后链重置，但未重新部署，前端仍用旧地址。**结论**：每次重启节点后必须重新执行 deploy:localhost + deploy:p9，**并重启前端 dev**，再强刷页面。
- **谁生成、谁使用**：部署脚本写 `deployments/31337.json` 并生成前端 `deployments.json`；前端只读；以当前节点上最后一次成功部署为准。

**节点重启 = 链重置：可验证判定三连**（任一成立即按「从零开始」走：起节点 → deploy:localhost → deploy:p9 → **重启前端 dev** → MetaMask 31337 → 强刷）：

| 判定项 | 如何验证 |
|--------|----------|
| /diagnostics 读到的 blockNumber | 归零或比上次明显变小 → 链已重置 |
| hardhat node 启动日志 | 重新出现「Accounts」「Private Keys」那段 → 本次会话为新区块链 |
| deployments/31337.json 与前端 | 地址与 `frontend/src/contracts/deployments.json` 中 31337 不一致 → 部署与前端不同步 |

**结论**：以上**任一成立**，都按「从零开始」执行（Part 1 第四节），且**必须重启前端 dev**，不能只强刷。

## 二、红字与「点不了确认」

- **长红字（Contract read failed...）**：RPC/合约读不到；按下面「标准操作顺序」做一遍即可。
- **「Blocked: Wallet network does not match node」**：钱包网络与节点/合约未对齐，前端故意禁用操作；对齐后即可点击。
- **红色横幅「链与合约地址不一致」**：当前链上不存在前端使用的合约地址；按标准操作顺序执行并强刷（Ctrl+Shift+R）。

## 三、标准操作顺序

| 步骤 | 做什么 | 怎么确认成功 |
|------|--------|--------------|
| 1 | 启动节点（保持运行） | `npx hardhat node`，看到 `Started HTTP and WebSocket JSON-RPC server at http://127.0.0.1:8545/` |
| 2 | 部署合约（新开终端，项目根目录） | `npm run deploy:localhost`，再 `npm run deploy:p9` |
| 3 | **重启前端 dev**（若前端已先启动） | **必做**：部署会更新 `deployments/31337.json` 并同步到前端 `deployments.json`，但前端在**构建/启动期**读取该文件（且可能被 Vite 缓存），故**部署后必须停止再启动 `npm run dev`**，不能只强刷；否则易出现「链与合约地址不一致」或读旧地址。 |
| 4 | MetaMask 设成本地链 | RPC URL = `http://127.0.0.1:8545`，Chain ID = `31337` |
| 5 | 强刷页面 | 浏览器 **Ctrl+Shift+R**（Mac Cmd+Shift+R） |

可选校验：打开 `/diagnostics`，确认 Read chainId = Wallet chainId = Yes、Deployments = Yes。一键：节点已起时可执行 `npm run local:prereq`。

## 四、从零开始（全部终止后再按顺序启动）

关掉 Hardhat 节点与前端后：终端 1 `npx hardhat node` → 终端 2 `npm run deploy:localhost`、`npm run deploy:p9` → 终端 3 `cd frontend && npm run dev`（若此前前端已启动则**必须先停再启**）→ MetaMask 选 RPC http://127.0.0.1:8545、Chain ID 31337 → 打开 Dashboard 并强刷。验证：/diagnostics 三项 Yes；Dashboard 无红字、可点击 Supply。**一键脚本（Windows）**：`npm run local:restart` 或 `scripts\local-restart.bat`。

**健康状态（Healthy Local）定义**：① node 在跑；② deployments 已同步（deployments/31337.json 与 frontend 一致）；③ 部署后前端已重启；④ /diagnostics = Yes/Yes/Yes；⑤ Supply 的 happy path 可完成一次（含 Approve）。若 `npm run local:prereq` 或 `npm run local:restart` 在结尾输出 **HEALTHY_LOCAL=true/false**，则便于脚本/CI 判断是否可跑 E2E 或门禁。

## 五、Console「MetaMask - RPC Error: Internal JSON-RPC error」

含义：MetaMask 连不上 RPC。原因通常为：(1) 节点没在跑；(2) MetaMask 网络未指到 127.0.0.1:8545、31337。按第三节顺序做；更细排查见 Part 2 §5。

## 六、常见一句答

| 问题 | 答案 |
|------|------|
| 合约地址以哪个为准？ | 当前节点上最后一次 deploy:localhost + deploy:p9 生成的地址；前端用此次写进的 `frontend/src/contracts/deployments.json`。 |
| 为什么「链与合约地址不一致」？ | 多半节点重启过、未重新部署。 |
| 红字/点不了确认？ | 按 Part 1 第三节标准操作顺序做一遍并强刷。 |
| Console 一直 Internal JSON-RPC error？ | 确认节点在跑、MetaMask RPC = http://127.0.0.1:8545、Chain ID 31337，强刷。 |

## 2. 合约地址表（以 deployments/31337.json 为准）

- **权威来源**：`deployments/31337.json`（部署脚本写入）；前端地址由 `scripts/_lib/export.ts` 同步到 `frontend/src/contracts/deployments.json`。
- **前端结构**：`deployments.json` 为多链键值表 `Record<chainId, Deployments>`，键为字符串（如 `"31337"`）；前端通过 `getDeployments(chainId)` 读取，类型见 `frontend/src/contracts/deployments.ts`。

**新增合约/新增键名时必须**：① 更新 **Deployments 类型**（`frontend/src/contracts/deployments.ts`）；② 更新 **DeploymentsJson**（`scripts/_lib/export.ts`）；③ 确保部署脚本写入 **deployments/31337.json** 对应键；④ export 生成 **frontend deployments.json** 与所需 **ABI**；⑤ 若有展示/校验，更新 **/diagnostics** 显示与 **verify:consistency** 检查项。缺一易导致类型或运行时不一致。

## 3. 配置文件与数据流

节点 RPC/Chain ID：`hardhat.config.ts` → localhost。前端 RPC/链：`frontend/src/config/network.ts`。部署结果：`deployments/31337.json`；前端地址：`frontend/src/contracts/deployments.json`。禁止在业务代码中硬编码 127.0.0.1:8545 或 31337；用 network.ts 常量或 getRpcUrl(LOCAL_CHAIN_ID)。E2E/CI 见 e2e/fixtures.ts、configs/localChain.mjs。

**链下配置（与代码一致）**：部署/门禁脚本通过 **loadProfile(chainId)** 唯一定义；profile 来自 **configs/profiles/\<mode\>/profile.json**（可选覆盖同目录下 \<chainId\>.json）。储备参数路径由 **profile.reservesConfigPath** 指定；本仓 mock 为 `scripts/config/reserves.31337.json`。若 profile 未指定，deploy 回退为 **scripts/config/reserves.\<chainId\>.json**（见 scripts/deploy/deploy.ts、scripts/config/loadProfile.ts）。

**部署与一键命令（以 package.json 为准）**：`deploy:localhost` → `scripts/deploy/deploy.ts`；`deploy:p9` → `scripts/deploy/deploy-p9.ts`；`local:prereq` → `scripts/demo/run-local-prereq.mjs`；`local:restart` → `scripts/local-restart.ps1`（Windows 下可执行 `scripts\local-restart.bat`）。**local-restart** 会结束 8545/5173 进程 → 起节点 → deploy:localhost + deploy:p9 → **verify:consistency**（核对 deployments/31337.json 与 frontend 地址、链上 code）→ 起前端；地址与 ABI 由 exportArtifacts 从部署产物同步到 frontend/src/contracts/deployments.json 与 frontend/src/abis/*.json。

| 用途 | 路径 | 谁写/谁读 |
|------|------|-----------|
| 根目录部署产物 | `deployments/31337.json` | 部署脚本写；脚本/CI 读 |
| 前端地址 | `frontend/src/contracts/deployments.json` | 由 `scripts/_lib/export.ts` 从 deployments/ 同步；前端通过 getDeployments(chainId) 只读 |
| 前端 ABI 文件 | `frontend/src/abis/TestToken.json`、`SimpleLending.json`、`GovToken.json`、`GovernorP9.json` | 由 export 从 artifact 写出（LendingPoolImpl→SimpleLending.json，GovernanceToken→GovToken.json）；P9 部署后含 GovernorP9、GovToken |
| 前端 ABI 引用 | `frontend/src/contracts/abis.ts` | 统一导出 ABIS.TestToken、ABIS.SimpleLending、ABIS.GovToken、ABIS.GovernorP9；业务逻辑仅通过 abis.ts 引用 ABI |

**地址键名**（与 deployments/31337.json、Deployments 类型一致）：chainId、usd8Address、wethAddress、simpleLendingAddress、aTokenAddress、variableDebtTokenAddress、oracleRouterAddress、proxyAdminAddress、configuratorAddress、mockAggregatorAddress、governanceTokenAddress、timelockAddress、governorAddress、emergencyModuleAddress。

## 3. 前端–后端接口边界

- **前端**：通过 ethers Provider + getDeployments(chainId) 取地址，ABI 从 abis.ts 引入；不直接读 deployments/ 目录。
- **后端/脚本**：deploy 写 deployments/31337.json，export 同步到 frontend。链下配置唯一入口为 **loadProfile(chainId)**（profile 来自 configs/profiles/\<mode\>/profile.json）；储备路径由 profile.reservesConfigPath 指定，未指定时回退为 scripts/config/reserves.\<chainId\>.json。
- **规范**：新增合约或地址时，DeploymentsJson 与前端 deployments 两处同步；ABI 由 export 从 artifact 写出。详见 [06-AUDIT-SUITE.md](06-AUDIT-SUITE.md) Part F。

## 4.2 调试工作（问题发生时的执行顺序）

**原则**：**先用 GATE 五项（CHAIN_ID_OK / RPC_OK / DEPLOYMENTS_SYNC_OK / READ_CONTRACT_OK / HEALTHY_LOCAL）门禁化判断**，任一项失败即走本文「最短修复路径」；全部通过后再查前端/合约逻辑。禁止在未完成 4.1 或 GATE 未过的前提下长时间排查业务代码。

| 顺序 | 动作 | 命令/位置 | 说明 |
|------|------|-----------|------|
| 1 | **确认节点在跑** | 终端 1 保持 `npx hardhat node`；或重新执行 | 节点退出则链重置，必须重新 deploy:localhost + deploy:p9 |
| 2 | **确认部署与前端地址一致** | `deployments/31337.json` 与 `frontend/src/contracts/deployments.json` 中 31337 的地址一致 | 若不一致：重新执行 deploy:localhost、deploy:p9（export 会同步到前端），重启前端 dev 并强刷 |
| 3 | **确认钱包网络** | MetaMask：RPC = http://127.0.0.1:8545，Chain ID = 31337 | 「Blocked: Wallet network does not match node」必先对齐此处 |
| 4 | **强刷页面** | 浏览器 Ctrl+Shift+R（Mac Cmd+Shift+R） | 排除缓存导致的旧地址/旧链 |
| 5 | **诊断命令（按需）** | 见下表 | 用于定位 RPC/读合约/部署一致性 |

**诊断命令速查**（均需节点已起；除 verify:consistency 外均需 `--network localhost`）。上述命令即 **GATE 五项** 的实操验收；以下「关键字段/期望」满足即判通过：

| 命令 | 用途 | 关键字段/期望输出（缺一即异常） |
|------|------|--------------------------------|
| `npm run diagnose:dashboard` | 诊断前端读链/读合约是否正常 | 输出含 **chainId=31337**、**rpc=http://127.0.0.1:8545**（或等价）、**deployments=OK**（或地址数量匹配）、**readContract=OK**（至少能读一个 view） |
| `npm run sentinel:read` | 哨兵读诊断（链/部署/前端一致性） | 同上；与 diagnose 互补，用于 CI/本地自检 |
| `npm run verify:consistency` | 校验节点 chainId、deployments、前端地址一致 | **exit 0** 表示一致；非 0 即需按 4.1 重做 |
| 打开 `/diagnostics` | 前端自检：Read chainId、Wallet chainId、Deployments | **三项 Yes** 即通过；任一 No 则按 4.2 顺序排查 |

**常见现象与对应动作**（与 Part 1、Part 2 §5 一致）：

| 现象 | 首选动作 | 最短修复 |
|------|----------|----------|
| Contract read failed / 长红字 | 按 4.1 从 2→3→4→5→6 重做；强刷；必要时 `npm run local:restart` | `npm run local:restart` → MetaMask 31337 → **重启前端** → 强刷 |
| Balance fetch failed / Balances not loaded | 确认 RPC、Chain ID 31337；deploy 后**重启前端**再强刷 | deploy:localhost + deploy:p9 → **重启前端 dev** → 强刷 |
| Blocked: Wallet network does not match node | MetaMask 切换到本地网络（RPC 127.0.0.1:8545，Chain ID 31337） | MetaMask 切链 → 强刷 |
| 链与合约地址不一致（红横幅） | 重新 deploy，**必须重启前端 dev**，强刷 | **`npm run local:restart`** → 重启前端（若脚本未含）→ MetaMask 切链 → **Ctrl+Shift+R** |
| 按钮灰、点不了 | 先 /diagnostics 三项 Yes；再查 Approve、储备暂停等（见 [10-TROUBLESHOOTING-AND-LIMITATIONS.md](10-TROUBLESHOOTING-AND-LIMITATIONS.md) §三） | /diagnostics 通过后再试；缺 Approve 则先 Approve |
| Console -32002 / too many errors | RPC 可达、节点在跑；避免重复弹窗 | **先关 MetaMask 弹窗**再强刷；必要时 Reset account（仅当前网络） |

**证据与留证**：调试中若需留证，可使用前端 **/diagnostics** 页的「Session evidence」「Download」「Copy debug bundle」。与 evidence-pack 对齐的**最小证据包字段**（便于回溯）：**chainId + rpc**；**deployments/31337.json 的 SHA256**（或 content-hash）；**/diagnostics 截图**（三项 Yes）；**hardhat node log 片段**（含 chainId/Accounts）；若失败则 **tx hash + revert reason**。E2E 与门禁留证见 [03-08-deployment-runbook.md](03-08-deployment-runbook.md) §8、[11-FULL-LINK-TEST-CHECKLIST.md](11-FULL-LINK-TEST-CHECKLIST.md)。
