## 执行纪律（防遗漏，AI 与人同守）

- **完成一部分功能就要测**：每完成**当前 P** 的「升级内容」与「交付物」后，**必须先执行该 P 的「打勾测试」**（脚本测试、部署、冒烟、单元/集成测试等），**全部通过后再进入下一 P**。不得未跑测试或测试未通过就进入下一阶段。
- **测试即打勾**：每项打勾测试需**实际执行**（如 `npx hardhat test`、`npm run deploy:localhost`、`npm run smoke:e2e` 及该 P 所列命令），通过后再将 `[ ]` 改为 `[x]`。
- **文档不够细时**：以《03-五大核心模块》《05-升级后架构与模块化》《07-升级后智能合约清单》及该 P 相关的 02/06/08/09 为准补全，不得自行省略与设计不一致的部分；有歧义查《00-术语与约定》或《13-审计与对照》。
- **涉及安全时**：凡该 P 涉及预言机、权限、清算、利率、升级等，**须对照《09-安全设计-清单》§2 攻击面与防护**；各 P 与 09 的对应见文末 **P0–P10 与 09 安全对应表**。
- **涉及 Mock 时**：凡 **P2/P4/P5/P6/P7/P8** 涉及利率、代币、预言机、清算等外部依赖，**必须查《15-Mock与测试环境清单》**（§1 依赖表、§2 参数表、§3 场景表）；各 P 所需 Mock 见下文「升级内容」中「Mock 要求」及文末 **P0–P10 与 15 Mock 对应表**。
- **不跳阶段**：严格按 P0→P1→…→P10 顺序执行（除文档明确标注可选外）。

### Dual-Mode（Mock ↔ Real）· 本地优先与验收

- **收口原则**：同一套代码通过 **MODE**（mock / real）切换；**默认 MODE=mock**，**本地优先**：在 localhost(31337) 完整可测、可跑、可留证；**MODE=real 仅作未来上线配置，不得成为本地门禁前置**。
- **配置唯一入口**：所有 deploy / governance / security-gate / scenario 脚本**只能通过 loadProfile(chainId) 取配置**，禁止散落 env 分支。Profile：**configs/profiles/{mock,real}/**，入口 **scripts/config/loadProfile.ts**。
- **本地门禁**：**MODE=mock** 下 `npm run p10:gate` **必须 exit 0**，并生成 evidence-pack（含 **manifest sha256 锚点**）。

## 前端与后端顺序说明（P0–P10 与前端 P11–P20）

### P0–P10 以「后端」为主，前端嵌在 P5/P9/P10

- **P0–P10** 的「升级内容」与「交付物」以**合约、链上、脚本、测试**为主（即**后端**）；**前端**在以下 P 有明确集成与验收：
  - **P0**：打勾含「前端可完成一次完整 supply → borrow → repay → withdraw」（当前 Demo 前端）。
  - **P1**：交付物含「前端/测试使用代理地址调用」，行为与升级前一致。
  - **P5**：交付物与打勾含**多资产 UI**、aToken/debtToken 展示、**前端集成与前端验收**。
  - **P9**：打勾含**治理 UI** 可查看提案、投票、执行状态。
  - **P10**：打勾含**前端集成验收**（多资产 UI、治理 UI、代理地址切换）。
- 因此：**P0–P10 不是「纯后端」**，而是「后端为主 + P5/P9/P10 含前端集成与验收」。

### 升级顺序：先完成后端，再完成前端（推荐两种方式）

**方式一（推荐）：按 P 先后端再前端**

- 每个 P 内：**先完成该 P 的合约/交付物与链上（或脚本）测试**，再完成**该 P 的前端集成与验收**（若该 P 有前端项）。
- 例如：P5 先完成 aToken/debtToken 合约与集成测试 → 再完成 P5 多资产 UI 与前端验收；P9 先完成 Governor/Timelock/Emergency → 再完成 P9 治理 UI。
- 优点：每阶段都可端到端演示；前端不阻塞后端，后端也不等全部 P 才做前端。

**方式二：P0–P10 全部后端完成后，再集中做前端**

- 先按 P0→P10 完成**全部**合约、脚本、链上/集成测试（前端仅保持「能调通」即可）；P10 打勾后再集中做**前端升级**（全局框架、Dashboard、Markets、Activity、Settings、交易弹窗、风控可视化、Dev Panel 等）。
- 优点：后端一次性闭环，前端排期清晰；缺点：前端演示会较晚，需在 P5/P9 时用简易前端或脚本验证。

**结论**：**先完成后端（合约/链上/测试），再完成前端**——要么按 P「先该 P 后端再该 P 前端」（推荐），要么 P0–P10 全部后端完成后再集中做前端。

### 前端是否单独编号 P11–P20（可选）

- **不单独编号（现状）**：前端工作嵌在 P5/P9/P10，顺序即「先完成该 P 后端，再完成该 P 前端」；验收以本文 P5/P9/P10 打勾为准。
