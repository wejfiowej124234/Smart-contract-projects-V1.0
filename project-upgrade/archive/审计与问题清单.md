## 2) 发现的问题与缺口

### 2.1 文档与流程

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| **缺少升级流程文档** | 高 | 升级方案仅提到「部署/升级 runbook」「07-upgrade-governance」，但本包内无 step-by-step 的合约升级与回滚流程。→ **已补充**《升级流程.md》。 |
| **阶段验收标准未成文** | 中 | 各阶段「完成」的 checklist（测试通过、文档就绪、谁签字）未单独列出，易导致验收口径不一致。建议在《升级方案.md》每阶段下增加「验收标准」小节，或单独《阶段验收清单.md》。 |
| **引用目标仓库路径易混淆** | 低 | 文中多次写 docs/07-upgrade-governance.md、08-deployment-runbook 等，这些是**升级后**目标仓库的 docs，不是 project-upgrade 内文件。建议在 README 或升级方案开头注明「本包为规划文档；07/08 等为升级后仓库中的文档路径」。 |

### 2.2 技术与设计

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| **存量数据迁移未说明** | 中 | 从当前 SimpleLending（无代理）迁移到「代理+Pool」时，若存在链上存量用户/仓位，是否迁移、如何迁移（快照+新池 vs 从零开始）未写清。建议在《升级方案.md》阶段 1 或《当前项目现状.md》中明确：当前 Demo 为本地链、可视为无存量，或注明「生产迁移需单独方案」。 |
| **库与合约部署口径** | 低 | 《升级后智能合约清单》中 ReserveLogic、UserConfiguration 等为库（不单独部署），《升级后目录结构》中为 .sol 文件并列在 core/ 下，无矛盾但可在清单中注明「库：不单独部署，内联或 delegatecall」。 |
| **L2 / 多链部署** | 低 | 目录与清单提到 L2（SequencerUptimeGuard）、crosschain 可选，但升级方案各阶段未明确「先单链主网还是先 L2」。属产品路线选择，建议在升级方案「阶段 6」或「依赖关系」中一句话约定。 |

### 2.3 一致性与可追溯

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| **合约数量区间** | 低 | 清单写「约 27–32 个」，与 core 9 + tokens 3+ + oracle 5 + governance 4 + upgrade 2–3 + libs 4 加总一致；aToken/debtToken 按资产增加会超过 32，已说明，无错误。 |
| **架构图与模块化** | 无 | 升级后架构图与升级后模块化设计中的模块划分、依赖关系一致，无冲突。 |
