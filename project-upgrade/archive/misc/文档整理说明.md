| 场景 | 规范 |
|------|------|
| **引用编号文档** | 写《00-术语与约定》或《11-升级阶段清单-P0至P10》；或「00」「11」；与 00 §1 文件名一致。 |

| **阶段与 P** | 叙事用「阶段 0–6」，打勾用「P0–P10」；不混用「阶段 P3」。见 00 §3。 |
| **链接** | README 内使用相对链接（如 [00-术语与约定](../00-术语与约定.md)，从 misc 指向根目录时加 `../`）；其他文档引用时写《文档名》或「见 xx §n」。 |

## 四、可合并建议

| 方案 | 建议 | 理由 |
|------|------|------|
| **全面审计报告 + 14-企业级审计报告** | **不合并** | 职责不同：全面审计 = 顺序+内容+前端+缺口；14 = 清晰度+缺口+文档关系。合并后 14 过长且两种审计口径混在一起。 |
| **前端企业级审计报告 + 全面审计报告** | **不合并** | 前端审计为专项，全面审计为综合；各自独立便于按「前端」与「全包」查阅。 |
| **P0-P10前端覆盖与文档整理检查 + 企业升级文档-问题与整改** | **可选合并** | 两者均为「检查/整理」类，可合并为一份《文档与前端覆盖检查》（含 P0–P10 前端覆盖、文档合并/删除建议、企业文档问题与整改）。合并后根目录少 1 个文件，但当前两份职责略不同（一偏前端覆盖与整理，一偏企业文档符合性），**建议保留两份**，便于按需查阅。 |
| **文档整理说明 + README** | **不合并** | README 为入口与文档表；本文为整理专项说明（排序、引用、删并）。合并会使 README 过长。 |

**结论**：**不建议合并**现有文档；保持根目录 00–15、README 与 misc/ 内无编号文档（迁移方案、前端方案、UI-UX、各审计与检查）独立，便于按编号与用途查阅、审计溯源清晰。

## 五、推荐阅读与使用顺序

1. **首次进入**：README → 00-术语与约定。
2. **理解升级**：01 → 02 → 10 → 11（基线 → 资产 → 阶段方案 → 打勾清单）。
3. **做设计/实现**：按需 03、04、05、06、07、08、09、15；做升级步骤时 12。
4. **审计与合规**：13、14、全面审计报告、前端企业级审计报告；文档整理与前端覆盖见 P0-P10前端覆盖与文档整理检查、企业升级文档-问题与整改、本文。
5. **前端**：前端升级方案（§10 为验收清单）→ UI-UX设计方案；前端审计见前端企业级审计报告。
