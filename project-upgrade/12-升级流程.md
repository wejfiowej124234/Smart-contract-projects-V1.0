# 升级流程（合约与实现升级操作指南）

> 本文档描述「代理模式下实现合约升级」的完整流程、验收与回滚，供执行与审计使用。与《10-升级方案》中的阶段规划配套；**目标仓库**中的 docs/12-PROTOCOL-DESIGN §07（升级与治理）、**docs/03-08-deployment-runbook.md** 可引用或合并本文内容。

---

## 1) 适用范围

- **实现合约升级**：通过 TransparentProxy / UUPS 将代理指向新的实现合约（Pool、PoolConfigurator、Liquidation 等）。
- **参数/配置变更**：通过 PoolConfigurator 修改 LTV、LT、利率策略等，走治理（Governor + Timelock），不在此文「升级」步骤内，见下文 5.2。
- **首次部署**：新环境首次部署代理+实现，见 scripts/deploy 与**目标仓库**《docs/03-08-deployment-runbook.md》；本文侧重「已有代理，更换实现」的流程。

---

## 2) 角色与权限

| 角色 | 权限 | 说明 |
|------|------|------|
| **ProxyAdmin 所有者** | 调用 upgrade/upgradeAndCall | 通常为多签或 Timelock，不推荐 EOA |
| **Timelock** | 排队并执行升级交易（若升级权委托给 Timelock） | 延迟执行，给社区/监控留窗口 |
| **Guardian** | 紧急 Pause、不执行逻辑升级 | 不能改实现地址，只能暂停 |
| **审计/运维** | 只读验证、监控 | 不持私钥，参与验收与告警 |

---

## 3) 实现合约升级流程（Step-by-Step）

### 3.1 准备阶段

1. **新实现合约开发与测试**
   - 在 feature 分支完成新实现（如 PoolV2.sol）。
   - 保证接口兼容：代理调用的入口（supply/withdraw/borrow/repay 等）签名与存储布局兼容；若有新存储变量，仅追加在末尾，避免插槽冲突。
   - 单元测试 + 集成测试 + 不变量测试通过；CI 绿。
   - 内部/外部审计完成，已知问题修复或文档化接受。

2. **部署新实现**
   - 在目标网络（测试网/主网）部署**新实现合约**（不替换代理）。
   - 记录新实现合约地址、部署 tx、block；可选：etherscan 验证源码。

3. **升级提案（若走治理）**
   - 撰写提案：升级原因、新实现地址、影响范围、测试与审计结论链接。
   - 通过 Governor 提交：calldata 为 ProxyAdmin.upgrade(proxy, newImplementation) 或 upgradeAndCall(proxy, newImplementation, initData)。
   - 投票期结束且通过 → 提案进入 Timelock 队列。

### 3.2 执行阶段

4. **Timelock 执行窗口**
   - 等待 Timelock delay 届满。
   - 在执行窗口内调用 Timelock.executeTransaction：目标=ProxyAdmin，calldata=upgrade(proxy, newImplementation)。
   - 若需初始化（如迁移数据、重算 index），使用 upgradeAndCall(proxy, newImplementation, initData)；initData 仅调用一次，需在实现合约中做 idempotent 或 only-once 保护。

5. **链上验证**
   - 读代理 implementation()（或 TransparentProxy 的 implementation slot），确认为新实现地址。
   - 用代理地址调用关键 view（如 getPoolInfo、getUserPosition），结果符合预期、无 revert。
   - 可选：在测试网用前端/脚本跑一条 supply/withdraw 路径，确认端到端正常。

- **实现升级演练留证（本地链 31337）**：脚本 `scripts/governance/proxy-upgrade-drill.ts`（部署新 LendingPoolImpl，经 Governor 执行 ProxyAdmin.upgrade(proxy, newImpl)）；执行命令 `npm run governance:proxy-upgrade-drill`；tx/block 与 getProxyImplementation 读值见 **docs/archive/audits/P9-ONCHAIN-GOVERNANCE-ACTIVATION-FINAL-CHECK.md** §3.7。

### 3.3 验收与观察

6. **验收清单**
   - [ ] 代理 implementation 已指向新实现。
   - [ ] 关键 view 与升级前一致或符合设计（如 index 延续）。
   - [ ] 至少一笔写操作（supply/repay 等）成功且事件/状态正确。
   - [ ] 监控/告警无异常（HF 分布、坏账、预言机偏离等）。
   - [ ] 文档更新：实现版本、升级 tx、负责人、日期。

7. **观察期**
   - 建议 24–72 小时内密切监控；若有异常，执行回滚流程（见下）。

## 4) 回滚流程

- **触发条件**：升级后出现严重 bug、异常状态、或审计/社区发现不可接受风险。
- **回滚步骤**：
  1. 必要时 Guardian 先 **Pause** 相关合约，止损。
  2. 通过 ProxyAdmin 再次 **upgrade(proxy, previousImplementation)**，将代理指回上一版实现地址（需在升级前妥善保存）。
  3. 链上验证 + 验收清单再跑一遍。
  4. 事后分析：根因、时间线、改进措施（测试/流程/权限）。
- **注意**：回滚后，升级后新产生的状态（若写入新实现新增的存储）可能对旧实现不可见或不可用，设计时需考虑存储布局与兼容性，必要时在旧实现中保留「最小可读」或仅回滚关键入口。

## 5) 与其他流程的关系

### 5.1 参数/配置变更（非实现升级）

- **流程**：Governor 提案 → 投票 → Timelock 排队 → 执行时调用 **PoolConfigurator**（setLTV、setLiquidationThreshold、setInterestRateStrategy 等）。
- **不涉及**：ProxyAdmin、implementation 地址不变；仅数据/配置变化。
- **文档**：见《10-升级方案》阶段 5 与**目标仓库** docs/12-PROTOCOL-DESIGN.md §07（升级与治理）。
- **留证（本地链 31337）**：脚本 `scripts/governance/first-proposal-setltv.ts`（setLTV 76）、`scripts/governance/second-proposal-setlt.ts`（setLiquidationThreshold 81）；执行命令 `npm run governance:first-proposal`、`npm run governance:second-proposal-setlt`；tx/block 与关键读值见 **docs/archive/audits/P9-ONCHAIN-GOVERNANCE-ACTIVATION-FINAL-CHECK.md** §3.3、§3.6。

### 5.2 紧急暂停（不升级实现）

- **流程**：Guardian 调用 EmergencyModule 或 Pausable 的 pause()。
- **不涉及**：代理与实现地址均不变。

## 7) 首次部署前检查清单（新环境首次部署代理+实现时执行）

**适用范围**：新网络/新环境**第一次**部署代理与实现（非「已有代理、换实现」）。执行部署脚本前逐项打勾。

| 类别 | 检查项 | 打勾 |
|------|--------|------|
| **环境与网络** | 当前网络与《01-当前项目现状》§2 环境与网络清单一致（local/testnet/mainnet）；chainId、RPC 正确；.env 或 hardhat.config 的 defaultNetwork 与目标环境一致 | [ ] |
| **依赖与版本** | Node/Hardhat/Solidity 版本符合项目要求；`npm ci` 或 `npm install` 已执行；无已知漏洞依赖（可选：npm audit） | [ ] |
| **Key 与权限** | 部署用私钥或 KMS 已就绪；testnet/mainnet 与 local 的 key 隔离；多签/ Timelock 地址（若需）已确定 | [ ] |
| **Config** | scripts/config（reserves）、configs/profiles（profile）下当前环境的配置文件存在（如 reserves.31337.json、profile.json）；资产列表、LTV/LT、Oracle 映射等与《02-资产清单-抵押与借贷》《15-Mock与测试环境清单》对齐；储备路径见 profile.reservesConfigPath 或 scripts/config/reserves.\<chainId\>.json（与 docs/09 一致） | [ ] |
| **Mock（本地）** | 若为 local：Mock 合约与《15-Mock与测试环境清单》§1、§2 一致；价格/代币初始化参数已设 | [ ] |
| **部署顺序** | 部署顺序已明确：实现合约 → 代理 → 初始化；或按目标仓库 **docs/03-08-deployment-runbook.md** 的「首次部署」章节执行 | [ ] |
| **导出与前端** | 部署脚本写 deployments/\<chainId\>.json，**scripts/_lib/export.ts** 同步到 **frontend/src/contracts/deployments.json** 并写出 ABI（与 docs/09 一致）；前端 RPC 与当前环境一致 | [ ] |
| **主网权限移交（H1 / Final Gate B1–B3）** | **主网部署前**：ProxyAdmin.owner、**Pool (LendingPool).owner**、PoolConfigurator.admin 须移交多签或 Timelock；不得长期由 EOA 控制；执行移交并记录（见 **docs/archive/audits/final-security-gate-mainnet.md**） | [ ] |

- 全部打勾后再执行首次部署；详细步骤以**目标仓库** **docs/03-08-deployment-runbook.md** 为准，本清单为最小必要检查。
