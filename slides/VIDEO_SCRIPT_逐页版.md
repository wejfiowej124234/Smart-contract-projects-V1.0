**页面标题**：Executive Summary（金融企业视角）

安全基线包括：ReentrancyGuard、防误操作的 Pausable/Ownable、以及 SafeERC20 等基础加固；前端侧包含网络检查与金额解析防护，降低常见集成风险。

合规性方面，我们明确说明了项目边界和风险范围，不做预言机、清算、多资产等超出题面要求的功能，避免过度设计和合规风险。

一句话总结：虽然这是 coding test，但交付物齐全、可复现、可验收，且能把风险边界与工程取舍讲清楚。

## 📄 第12页：合约业务规则

**页面标题**：合约：业务规则（核心）

**演讲稿**：

合约的核心业务规则设计如下：

采用单币种设计，USD8 代币同时作为抵押资产和借贷资产使用。

贷款价值比 LTV 设定为 75%，也就是说最大借款额度等于已存入金额乘以 75%，这是风险控制的核心参数。

借款操作有硬性检查：借款后总借款额不能超过最大借款额度，否则智能合约会直接 revert，把风险边界落在链上。

取款操作也有硬性检查：取款后用户仓位必须保持健康状态，即健康因子必须满足要求，否则也会 revert，防止过度杠杆。

一句话总结：借款和取款的风险控制不是由前端 UI 控制，而是由智能合约强制执行 revert，把关键约束落在链上并便于复核。

交易状态机是工程可靠性的核心机制。（指向状态图）这个状态图展示了完整的交易生命周期：从 idle 空闲状态，到 signing 签名中，到 pending 等待链上确认，最后到 confirmed 已确认或 failed 失败状态。

## 📄 第18页：合约安全组件

**页面标题**：合约：安全组件（为什么要加）

**演讲稿**：

安全组件方面，我们加入了几项常见的安全基线措施：

第一，ReentrancyGuard 防重入：对关键写函数做保护，用于降低重入类风险。

第二，Pausable + Ownable：提供紧急暂停开关，便于在发现问题时快速止损。

第三，SafeERC20：兼容一些非标准 ERC20 的返回值行为，降低转账兼容性踩坑风险。

从风险控制矩阵来看，我们识别了以下关键风险并进行了缓解：
- **资金安全风险**：通过 LTV 75% 硬约束和智能合约强制执行 revert 进行缓解，风险等级从高风险降至低风险
- **数据一致性风险（UI 漂移）**：通过三层 best-effort 刷新机制（confirmed 后刷新 / events 主路径 / 有界 backfill 兜底）降低概率；必要时允许用户 Refresh 复核
- **安全攻击风险**：通过防重入、安全转账、可暂停机制降低常见风险面
- **系统可靠性风险**：通过交易状态机与兜底刷新策略降低“卡住/延迟/读不到”的体验风险

边界声明：本项目明确不做预言机价格喂送、清算机制、多资产支持等功能，严格保持题面要求范围。这是加分项，说明我们明确知道项目边界和风险范围，避免过度设计和合规风险。

## 📄 第19页：前端读写分离

**页面标题**：前端：读写分离（provider vs signer）

**演讲稿**：

前端架构采用读写分离：读用 provider，写用 signer，避免把高不确定性的写流程污染读模型。

Read model：使用 provider + view calls 并发读取余额、pool、position、maxBorrow、maxWithdraw。

Write model：使用 signer 发交易，并对交易生命周期做状态管理，便于用户理解当前处于哪一步。

收益是：读模型不被写流程污染，并且在 confirmed(TX_CONFIRMATIONS) 后再触发一次 refresh，减少“写了但暂时读不到”的困惑。

## 📄 第20页：前端交易状态机

**页面标题**：前端：交易状态机（为什么不是"发完就算"）

**演讲稿**：

前端的交易状态机有多个阶段：idle、signing、pending、confirmed 或 failed（以及 pending 超时后的 stuck）。

这主要是为了应对真实世界的问题：用户可能拒绝签名，pending 可能很久，可能出现 speed up / replacement，还有 RPC 读延迟——confirmed 不等于立刻能读到。

从体验角度，状态机让用户对“我现在在签名/广播/确认/失败”有清晰认知。

这里要强调：区块链 UX 的不确定性更多来自钱包、网络、RPC，而不一定是代码写错。

## 📄 第21页：刷新策略（3层）

**页面标题**：刷新策略（3 层）

**切换提示**：切换到第21页，显示refresh-strategy图表

**演讲稿**：

刷新策略采用三层 best-effort 机制，按优先级排序：

（指向图表）第一层，confirmed 后刷新：交易 confirmed(TX_CONFIRMATIONS) 后触发 onConfirmed() 刷新读模型；写流程还会做 post-state verification（如果 RPC 读延迟较大，会标记 unverified 并提示手动 Refresh 复核）。

第二层，合约事件监听（主路径）：监听 Supplied/Withdrawn/Borrowed/Repaid 四个业务事件；事件回调会节流触发 refresh（避免频繁重渲染）。

第三层，兜底机制：节流的 block listener + 小范围 backfill。backfill 使用 queryFilter 在有界区间内回填（EVENT_BACKFILL_MAX_BLOCKS=2000），并用游标推进；兜底在 tx pending / dashboard loading 等情况下会关闭，避免无意义刷新。

证据点包括：frontend 的 useDashboard.ts / useActions.ts / App.tsx 实现了三层刷新与校验逻辑，config 下的 runtime.ts 配置了相关参数。

**停顿**：4-5秒，让观众理解三层机制

## 📄 第23页：前端 Approve 细节

**页面标题**：前端：Approve 细节（面试官爱追问）

**演讲稿**：

Approve 是面试官经常追问的点，也是 ERC20 交互里最常见的前置步骤之一。

哪些操作需要 approve：Supply（存入）和 Repay（还款）。原因是这些写操作内部会用到 transferFrom，需要依赖 ERC20 allowance。

前端策略是 approve-if-needed：如果 allowance 已经足够，就跳过 approve，减少用户操作；不足才发起 approve。支持 exact 精确授权和 infinite 无限授权两种模式，在安全与便利之间做取舍。并且兼容常见的“USDT 风格”实现：如果直接 approve(amount) 失败，会 fallback 到 approve(0) 再 approve(amount)。

## 📄 第24页：错误处理归一化

**页面标题**：错误处理：归一化（你会显得很工程化）

**演讲稿**：

错误处理做了归一化，目的是把用户能理解的提示、以及工程排查需要的细节分开。

目标是：把 provider / ethers / wallet 的错误统一成少量可解释、可展示的分类，同时保留原始错误信息用于排查。

主要分类包括：
UserRejected（例如错误码 4001）：用户拒绝签名/操作，属于正常分支；
Revert（例如 CALL_EXCEPTION / reverted）：合约执行失败，优先展示 revert 原因；
Rpc（timeout / network 等）：链路或节点问题，给出可操作的重试建议。

展示策略：UI 给用户一句话结论；技术细节保留原始错误便于排查；当 pending 超时或 RPC 失败时，提供明确的重试/刷新建议。
